# Capability reference

What this system does, the code that implements it, and the command that
validates it. Where a capability is implemented but not yet measured,
this document says so rather than the wording being softened elsewhere.

Status values used below:

- **Implemented and tested** — shipped and covered by an automated test.
- **Implemented — precise wording required** — shipped, but the obvious
  short description would overclaim; the accurate wording is given.
- **Implemented — not yet measured** — the machinery exists, the
  measurement does not.

Where a capability's evidence is a generated artifact, the command that
generates it is named. `docs/RESUME_EVIDENCE.md` derives a PASS/FAIL for
each of these claims from those artifacts and is regenerated by CI, so
this file and the evidence cannot drift apart silently.

## 1. Self-improving harness

**Status: implemented and tested**

### Implementation

| Piece | File |
|---|---|
| Proposer (spawns the `claude` CLI with SKILL.md appended) | `backend/app/meta_harness/proposer.py` |
| Outer loop that drives propose → validate → benchmark → update_frontier | `backend/app/meta_harness/outer.py` |
| The 11 override points that form the search space | `backend/app/meta_harness/harness.py` |
| Candidate source snapshotting and isolated loading | `backend/app/meta_harness/candidates.py` |
| The proposer's workflow contract | `skills/meta-harness-coding-agent/SKILL.md` |

The proposer reads the branch's own `evolution_summary.jsonl`,
`frontier_val.json` and per-trial traces, then writes a new
`agents/<name>.py` subclassing `CodingAgentHarness`. The 6 inner-loop
tools are a fixed contract it may not change.

### Validation

```bash
# offline: the loop runs, snapshots candidate source, evolves state
cd backend && uv run pytest tests/test_outer.py tests/test_proposer.py -q

# live: the real claude-CLI proposer writes an importable candidate
bash scripts/live_smoke.sh          # section 3
```

Key tests: `test_candidate_source_is_snapshotted_per_branch`,
`test_mock_outer_loop_produces_all_files`,
`test_claude_propose_fails_loudly_when_the_branch_handoff_is_missing`.

### Limitations

The search space is bounded to the 11 override points; a candidate
cannot change the tool contract, and validate-time enforcement rejects
one that tries.

## 2. Dual LangGraph execution

**Status: implemented and tested**

### Implementation

**Outer** — `backend/app/meta_harness/outer.py`, `OuterLoopRunner.build()`

```
START → propose → validate → benchmark → update_frontier ─┐
                                  ▲                        │ budget > 0
                                  └────────────────────────┘
                                            └→ END
```

**Inner** — `backend/app/meta_harness/inner.py`, `build_inner_graph()`

```
START → orient → plan → act → verify ─┬→ submit → END
                          ▲           │
                          └───────────┘  tests failed, retries remain
```

Both compile with a checkpointer; the outer loop passes its
`AsyncPostgresSaver` down into every inner trial.

### Validation

```bash
cd backend && uv run pytest tests/test_inner.py tests/test_outer.py \
                            tests/test_inner_checkpoints.py -q
```

`test_inner_graph_compiles_with_and_without_a_checkpointer` and
`test_benchmark_core_threads_the_checkpointer_into_every_trial` cover
the two-machine structure directly.

### Limitations

Both graphs compile without a checkpointer as well, for tests and
offline runs; in that mode nothing is persisted and neither branching
nor recovery is available.

## 3. Harness evolution across iterations

**Status: implemented and tested**

### Implementation

Each iteration appends one row to the branch's
`evolution_summary.jsonl` with the candidate, its parent, its measured
scores, and its delta against the measured prior best. Iteration 0 is
the benchmarked baseline, so the first candidate's delta is a real
comparison rather than a comparison against zero.

### Validation

```bash
cd backend && uv run pytest tests/test_outer.py -q
uv run meta-harness loop --proposer mock --mock-bench --budget 2 --fresh --run-name demo
cat runs/demo/threads/demo/evolution_summary.jsonl
```

`test_baseline_is_benchmarked_before_any_candidate` asserts the first
candidate's delta equals `candidate_accuracy - baseline_accuracy` and
that `status.json` records what it was compared against.

### Limitations

Deltas produced under `--mock-bench` are synthesized, not measured.
Every row carries `metrics_source`, and mock rows never aggregate with
measured ones.

## 4. PostgreSQL checkpoint history

**Status: implemented and tested**

### Implementation

`backend/app/meta_harness/persistence.py` (`AsyncPostgresSaver` on a
sized pool), `branches.py` (`get_state_history`,
`get_checkpoint_state`), `backend/app/event_loop.py` (keeps the server
on a psycopg-compatible event loop).

Both graphs are checkpointed. Inner-loop threads are namespaced
`inner::{run}::{branch}::{candidate}::{task}::trial-{n}`, so any inner
checkpoint is attributable to the exact trial that produced it.

### Validation

```bash
docker compose -f infra/docker-compose.yml up -d postgres
cd backend && uv run pytest tests/test_persistence.py tests/test_inner_checkpoints.py -q
uv run meta-harness checkpoints <run-name>
```

`test_checkpoints_persist_in_postgres`,
`test_inner_graph_transitions_persist_in_postgres`,
`test_two_branches_do_not_share_inner_checkpoint_threads`.

### Limitations

Postgres must be reachable. `GET /health` reports `persistence` and
`persistence_error`; a server started without a usable connection
degrades to in-memory checkpointing, and branching and recovery stop
working with it.

## 5. Historical branching

**Status: implemented and tested**

### Implementation

`backend/app/meta_harness/branches.py` (`worktree_add` →
`aupdate_state` → `ainvoke(None, fork_config)` in an `asyncio.Task`),
`backend/app/api/forks.py`, thread-scoped artifacts in
`backend/app/meta_harness/runs.py`.

The part that makes this a real search tree rather than a demo: every
artifact a branch writes is scoped to its LangGraph thread. Two branches
forked from the same checkpoint reach the same iteration number and
still keep separate pending-eval handoffs, frontiers, evolution logs,
proposer sessions, candidate directories and candidate source snapshots.

### Validation

```bash
cd backend && uv run pytest tests/test_branch_isolation.py \
                            tests/test_branch_persistence.py -q
API_URL=http://127.0.0.1:8000 uv run python scripts/acceptance_api_flow.py
cd frontend/dashboard && npx playwright test --project=live-backend
```

`test_same_iteration_branches_keep_separate_artifacts` reproduces the
exact race that used to corrupt a run and asserts it cannot happen.
`test_trajectory_survives_registry_reset` proves the branch tree is
reconstructable after a backend restart.

### Limitations

A running branch's asyncio task does not survive a backend restart. The
branch tree is reconstructed from durable metadata, and an interrupted
branch reports as `interrupted` rather than silently resuming.

## 6. Replay

**Status: implemented and tested**

### Accurate wording

Three different operations share the word "replay", and only one of them
supports the unqualified phrase *exact replay*. Say which:

> **Exact replay of a recorded execution.** A recorded inner-loop run
> re-executes from any of its stored checkpoints against its tape,
> reproducing the same transitions in the same order and the same final
> state byte-for-byte, with no model call issued.

> **Checkpoint recovery and branching from historical states.** Restoring
> a stored checkpoint returns byte-identical state; forking starts from
> exactly that state.

Do **not** describe `meta-harness resume`, or a fork, as reproducible.
Those re-enter the graph and issue *fresh* model calls: a new stochastic
execution that happens to start from an old state. A run that was not
recorded cannot be replayed exactly, and nothing claims otherwise.

### Implementation

| Piece | File |
|---|---|
| The effects boundary (live / recording / replaying) | `backend/app/meta_harness/effects.py` |
| The tape: entries, step marks, codecs, integrity | `backend/app/meta_harness/recording.py` |
| Record, replay, and verify | `backend/app/meta_harness/replay.py` |
| Node bodies routed through the boundary | `backend/app/meta_harness/inner.py` |

Every crossing into the world — model responses, tool inputs and outputs,
the workspace scan, the verify subprocess, the final-file snapshot — is
recorded in execution order, keyed by a SHA-256 over its *inputs*. Each
completed node is joined to the checkpoint it produced and to the hash of
the state it produced, which is what makes "replay from checkpoint X"
answerable.

On replay the graph **really runs**: nodes execute, the conditional edge
out of `verify` is recomputed from replayed state, LangGraph writes a
fresh checkpoint per super-step. Only the world is served from storage,
and `ReplayEffects` has no code path that reaches a provider — a property
of the code, asserted directly, not a promise in a docstring.

Five checks must all pass, or the command exits non-zero:
`no_divergence`, `node_sequence_identical`,
`per_step_state_hashes_identical`, `final_state_byte_identical`,
`tape_fully_consumed`.

Two determinism fixes were required and are load-bearing: `act` stamps
positional message ids and replaces rather than merges its trajectory
(without it `add_messages` mints a random UUID per message and no two
executions produce the same state), and `act` normalises state messages
back to the wire shape on the retry path.

### Validation

```bash
# offline: record and replay a real inner-loop run with a scripted model
cd backend && uv run pytest tests/test_exact_replay.py tests/test_recording.py \
                            tests/test_inner_messages.py -q

# against a live recording
uv run meta-harness inner --task task-001-fix-typo --candidate baseline --record
uv run meta-harness verify-replay runs/inner-test
uv run meta-harness replay <run> --checkpoint <id> --verify
```

`test_a_recorded_run_replays_exactly_from_the_start` and
`test_replay_from_every_recorded_checkpoint_reproduces_the_run` assert
the positive claim; `test_replay_effects_never_invoke_the_producer`
asserts no model call is possible;
`test_a_different_request_is_refused_by_the_tape` and
`test_a_different_routing_policy_fails_verification` assert the checks
can fail, which is what makes a pass mean something.

**Evidence artifact**: `docs/evidence/replay-verification.json`
(`meta-harness verify-replay`).

### Limitations

Exact replay applies to a run that was **recorded**. Recording requires a
checkpointer, and a tape holds every model response verbatim, so it is
opt-in (`--record`, `--record-trials N`) rather than always on.
Re-executing a *non*-recorded checkpoint issues fresh model calls and is
not reproducible.

## 6b. Git-style run versioning in PostgreSQL

**Status: implemented and tested**

### Implementation

`backend/app/meta_harness/versioning.py` is the read model;
`persistence.py`, `branches.py` and `runs.py` are the storage.

| Git | Meta-Harness |
|---|---|
| commit | a LangGraph checkpoint with an immutable `checkpoint_id` |
| parent commit | `parent_checkpoint_id` |
| branch ref | a `thread_id` in `runs/<run>/branches.json`, with its fork point |
| `checkout -b <sha>` | `branches.worktree_add(parent_checkpoint_id=...)` |
| working tree | `runs/<run>/threads/<thread>/`, private per branch |
| `git diff A B` | `versioning.diff_checkpoints` |

Nothing rewrites a checkpoint; a fork writes new ones on a new thread. So
a checkpoint id is a permanent address for one state, and
`verify_immutability` confirms a stored state still hashes to what it
hashed to.

### Validation

```bash
docker compose -f infra/docker-compose.yml up -d postgres
cd backend && uv run pytest tests/test_versioning.py -q
uv run meta-harness report version-graph <run-name>
```

`test_every_checkpoint_records_its_parent`,
`test_a_stored_checkpoint_still_hashes_to_what_it_hashed_to`,
`test_any_persisted_checkpoint_can_be_forked_from`,
`test_branch_history_survives_a_registry_reset`,
`test_branch_artifacts_report_each_thread_separately`.

**Evidence artifact**: `docs/evidence/version-graph.json`
(`meta-harness report version-graph <run>`).

### Limitations

A checkpoint written before any node ran carries no state; forking from
one starts a branch with an empty state. Fork from a checkpoint a node
produced. A running branch's asyncio task does not survive a restart —
the history does, and the branch reports as `interrupted`.

## 7. Pass-rate benchmarking

**Status: implemented — not yet measured**

### Implementation

The experiment runner (`backend/app/meta_harness/experiment.py`), the two
committed protocols (`benchmarks/pass-rate/config.json` and
`benchmarks/holdout/config.json`), the raw-row schema, the provenance
capture, the methodology checks and the summary derivation are all
implemented and tested. `meta-harness resume-experiment` runs the whole
sequence — evolve, select, measure, verify, report — as one command.

**No canonical 200-trial experiment has been executed**, because this
environment has no `ANTHROPIC_API_KEY` — the inner loop cannot issue a
single model call, so there is nothing to measure. There is no
placeholder pass-rate value anywhere in this repository, and
`docs/RESUME_EVIDENCE.md` reports the pass-rate rows as `UNSUPPORTED`
rather than softening them.

To produce the measurement:

```bash
echo 'ANTHROPIC_API_KEY=sk-ant-...' >> .env
uv run meta-harness resume-experiment --dry-run   # plan + cost estimate
uv run meta-harness resume-experiment             # evolve, measure, verify, report
```

### Methodology

The parts that make the number defensible, each checked mechanically:

- **Selection cannot see the test.** `pipeline.select_candidate` takes
  the outer loop's terminal state — validation accuracy measured during
  evolution — and nothing else. The canonical experiment runs afterwards
  with fresh independent trials. The decision and the table it was made
  from land in `runs/<run>/selection.json`.
- **Both arms ran the same protocol.** `check_protocol_equality` verifies
  identical task set, identical per-task trial counts, identical model,
  and a single `metrics_source` — published as `validation.json` and
  restated in `REPORT.md`. A failed check makes the CLI exit non-zero.
- **Incomplete arms are detected.** `trial_completeness` names missing,
  duplicated, unexpected and malformed trials. A row missing its outcome
  is unknown, not a failure.
- **Tasks are frozen and hashed.** `environment.json` records each task's
  `task.json` hash and every workspace/test file hash, plus commit SHA,
  dirty flag, model id, harness source hashes, interpreter and platform.
  Those are *byte* hashes, so `.gitattributes` pins the hashed trees to
  LF: without it a Windows checkout hashes every frozen task differently
  from a Linux one, and two runs of the identical protocol would disagree
  about what they measured.
- **Search and holdout are disjoint.** `check_task_set_isolation` runs
  before the pipeline starts; `resume-experiment` refuses to proceed on
  overlap.
- **Uncertainty is reported with its assumptions.** A 95% Wald interval
  on the difference of proportions, stated alongside the caveat that
  trials are clustered within tasks.

**Protocol**: [`benchmarks/pass-rate/README.md`](../benchmarks/pass-rate/README.md)
**Published results**: `benchmarks/results/` (currently empty)

### Validation

```bash
cd backend && uv run pytest tests/test_experiment.py tests/test_pipeline.py \
                            tests/test_resume_evidence.py -q
```

`test_summarize_accepts_no_target_or_expected_value` asserts by signature
inspection that `summarize()` takes only raw rows and labels — no target,
no expected value, no override.
`test_select_candidate_cannot_see_a_final_experiment` asserts the same
about selection. `test_summary_recomputes_identically_from_the_written_files`
proves any reader can re-derive the published number, and CI re-derives
every published summary on each push.

### Limitations

Trials are clustered within tasks, so the Wald interval understates
uncertainty. The canonical protocol measures the five search tasks the
proposer optimised against; the holdout protocol is the separate
generalisation measurement, and a smaller holdout delta is the expected
shape of the result rather than a failure.

## 7b. Experiment tracking (Weights & Biases)

**Status: implemented and tested — optional by design**

### Implementation

`backend/app/meta_harness/tracking.py` is the only module that may know
W&B exists. Core logic calls a small vocabulary — `log_trial`,
`log_iteration`, `log_frontier`, `log_experiment` — and those translate
into whatever `Tracker` is configured. Tracked: experiment config,
candidate iterations and their deltas, accept/reject, per-task results,
token usage, estimated cost, Pareto frontier membership, branch identity,
the two arms' pass rates and CI, and the result files as artifacts.

`metrics_source` rides along on every iteration point, so a
mock-benchmarked iteration can never be mistaken for a measured one in a
dashboard — the same rule the on-disk payloads follow.

**Optional means optional.** Off unless `--wandb` or
`META_HARNESS_WANDB=1`. `make_tracker` returns a `NullTracker` carrying a
reason when tracking is not requested, when `wandb` is not installed, or
when it fails to start, and never raises: a metrics backend that is down
must not fail a 200-trial experiment that costs money.
`WANDB_MODE=offline` is the supported no-network mode. No credentials are
read, written or logged.

```bash
uv sync --extra wandb                    # install the optional backend
WANDB_MODE=offline uv run meta-harness loop --wandb ...
```

### Validation

```bash
cd backend && uv run pytest tests/test_tracking.py -q
uv run meta-harness report wandb-check
```

The adapter's translation into W&B's API is asserted against an
**injected fake module**, so the tests need neither the package nor a
network. `test_core_modules_do_not_import_wandb` asserts the abstraction
holds. `test_tracking_is_off_by_default` and
`test_a_backend_that_fails_to_start_never_fails_the_run` assert the
optionality.

**Evidence artifact**: `docs/evidence/wandb-offline.json`
(`meta-harness report wandb-check`).

### Limitations

Nothing is logged to a W&B account in this repository, and no run URL is
published. The committed evidence is an offline probe.

## 8. Token and cost accounting

**Status: implemented and tested — no published totals**

### Implementation

`backend/app/meta_harness/metrics.py` records the Anthropic `usage`
block for every inner-loop call and aggregates to trial, candidate and
run level. Cost uses configurable pricing (`META_HARNESS_PRICING`); a
model with no configured price yields `cost_usd: null` and
`cost_complete: false` rather than `$0.00`. Mock and measured results
never mix: `aggregate_trials` refuses to fold rows whose
`metrics_source` disagrees.

### Validation

```bash
cd backend && uv run pytest tests/test_metrics.py -q
```

### Limitations

No aggregate token or dollar total is published anywhere in this
repository, because none has been measured.

## Design FAQ

| Question | Answer |
|---|---|
| What is the contribution? | The substrate: the Stanford meta-harness loop mapped onto two LangGraph state machines, which makes checkpointing, forking and concurrent search fall out of the framework rather than being bolted on. |
| What was the hardest bug? | Concurrent branches shared run-level artifacts, so a fork's proposer overwrote the root's `pending_eval.json` and the root then benchmarked a candidate it never proposed. Fixed by scoping every execution artifact to its LangGraph thread and snapshotting candidate source per branch. |
| How is branch isolation established? | `test_same_iteration_branches_keep_separate_artifacts` forks two branches from one checkpoint, runs both to the same iteration concurrently against a shared `AsyncPostgresSaver`, and asserts nothing is shared. |
| Why is the baseline benchmarked? | Otherwise iteration 1's delta is measured against zero and every first candidate looks like a huge win. The baseline runs the identical task/trial protocol and becomes the search-tree root. |
| Can a run be replayed? | A **recorded** run, yes, exactly: it re-executes from any of its stored checkpoints against its tape and reproduces the same transitions and the same final state byte-for-byte, with zero model calls. A run that was not recorded can have its state restored and its transitions read back, but re-executing it issues fresh model calls and is not reproducible. `meta-harness resume` is that second thing, and is never described as a replay. |
| Why is exact replay hard here? | Two sources of nondeterminism sit inside the framework rather than the model. `add_messages` mints a random UUID for any message without an id, and it merges rather than replaces, so a trimmed trajectory leaves a tail behind. `act` now stamps positional ids and clears before writing; both are load-bearing for byte-identical state. |
| How is the reported number kept honest? | Selection sees only validation results measured during evolution, never the final experiment. Both arms run one protocol, checked mechanically and published as `validation.json`. `summarize()` takes raw rows and labels — no target parameter exists — and CI re-derives every published summary from the committed trials. |
| What is the measured improvement? | Unmeasured. The runner and the whole pipeline are built and tested; no number is published, because the work was done without API credentials. `docs/RESUME_EVIDENCE.md` reports those rows as `UNSUPPORTED` rather than softening them. One command produces them: `uv run meta-harness resume-experiment`. |
